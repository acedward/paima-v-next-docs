Pool-Aware Batchers: Free Transactions for Stake Pool Delegators

2026年4月28日 · 約4分
EffectStream

The PoolDelegation primitive makes Cardano delegation data queryable from inside an EffectStream application. The most direct way to put that data to work for stake pool operators is the pool-aware batcher: an SPO runs a transaction batcher that covers gas fees, but only for users delegating to their pool. Delegators play for free; non-delegators get rejected before they ever enter the queue.

What the batcher does​

The EffectStream Batcher is a standalone service that accepts user inputs over HTTP, validates them, queues them, and submits them on-chain as a single batched transaction. The adapter is the extension point: by implementing a custom BlockchainAdapter, you control validation, serialization, and submission. For the delegation use case, we add a validateInput() method that queries the delegations table before accepting the input.

The delegation-aware adapter​

The core idea is to extend the default EVM adapter with a validateInput() method that checks the user's delegation status before accepting their input. The batcher reads from the same delegations table that the sync node writes to.

import {
  type DefaultBatcherInput,
  type ValidationResult,
  EffectStreamL2DefaultAdapter,
} from "@effectstream/batcher";
import { getDelegationsByAddress } from "@cardano-delegation/database";
import type { Pool } from "pg";

export class DelegationAwareBatcherAdapter
  extends EffectStreamL2DefaultAdapter
{
  private readonly dbConn: Pool;
  private readonly enabledPools: Set<string>;

  constructor(
    contractAddress: string,
    privateKey: string,
    fee: bigint,
    syncProtocolName: string,
    dbConn: Pool,
    enabledPools: string[],
  ) {
    super(contractAddress, privateKey, fee, syncProtocolName);
    this.dbConn = dbConn;
    this.enabledPools = new Set(
      enabledPools.map((p) => p.toLowerCase()),
    );
  }

  async validateInput(
    input: DefaultBatcherInput,
  ): Promise<ValidationResult> {
    // Look up the user's current delegation
    const delegations = await getDelegationsByAddress.run(
      { address: input.address },
      this.dbConn,
    );

    if (delegations.length === 0) {
      return {
        valid: false,
        error: "No delegation found for this address",
      };
    }

    // Check if the most recent delegation is to an enabled pool
    const latestDelegation = delegations[0];
    if (!this.enabledPools.has(latestDelegation.pool.toLowerCase())) {
      return {
        valid: false,
        error: `Not delegating to an enabled pool. ` +
          `Current pool: ${latestDelegation.pool}`,
      };
    }

    return { valid: true };
  }
}

getDelegationsByAddress returns delegations ordered by most recent first, so delegations[0] is always the user's current pool.

Configuring the batcher​

Wire the adapter into a batcher instance with the pool hashes you want to subsidize and a fee of zero:

const ENABLED_POOLS = [
  "7301761068762f5900bde9eb7c1c15b09840285130f5b0f53606cc57",
  "82ec502f8c0a51e7c0db410e6722dd42df3b8e11f48e833f9fdf2941",
];

const adapter = new DelegationAwareBatcherAdapter(
  process.env.L2_CONTRACT_ADDRESS!,
  process.env.BATCHER_PRIVATE_KEY!,
  0n,                        // Free for delegators
  "mainEvmRPC",
  dbConn,
  ENABLED_POOLS,
);

The fee: 0n is the whole point — the SPO covers the cost. Users delegating to the enabled pools get free transactions. Users delegating elsewhere get rejected at the validateInput() step before their input even enters the queue.

The validation flow​

When a user submits an input, the batcher pipeline processes it in order:

  1. Targeting — route to the correct adapter
  2. Signature verification — verify the user's wallet signature
  3. Input validation — validateInput() queries the delegations table by input.address and rejects if the user isn't delegating to an enabled pool
  4. Storage — if valid, the input is persisted to disk
  5. Batching — when criteria are met, inputs are serialized and submitted

A rejected input returns immediately:

curl -X POST http://localhost:3334/send-input \
  -H "Content-Type: application/json" \
  -d '{
    "data": {
      "address": "0x742d35Cc...",
      "addressType": 0,
      "input": "gameMove|x10y20",
      "signature": "0x...",
      "timestamp": "1234567890"
    }
  }'

# Delegator of an enabled pool:
# { "success": true, "hash": "0x..." }

# Anyone else:
# { "success": false, "error": "Not delegating to an enabled pool. ..." }

What SPOs can build with this​

The same primitive supports a small family of patterns beyond "free transactions":

  • Free game transactions — delegators play without paying gas; the SPO covers the cost (the example above).
  • Priority batching — delegators of partner pools get their inputs processed first.
  • Tiered access — different pools unlock different game features or areas.
  • Dynamic pricing — charge non-delegators a fee, subsidize delegators.

The configuration is the same in every case: add your pool hash(es) to ENABLED_POOLS, fund the batcher wallet, point your game's frontend at the batcher endpoint. The delegation check happens automatically on every input.
